# Ресерч

## Что WebAssembly ускоряет
Только счёт на процессоре внутри страницы (циклы, разбор, кодеки): обычно 1,2–3× к JIT-JS, без доступа к DOM —
каждый вызов DOM идёт через JS. Сеть, сборку модулей dev-сервером, растеризацию, отдельные процессы браузера не ускоряет.

## Дополнение: загрузка и кэш в headless (вопрос 2026-11-25)

Устройство сейчас: `launchStreamBrowser` (`lib/gateway/snapshot-browser.ts`) запускает Helium внутри процесса vite;
`StreamService.context` (`lib/stream/stream-service.ts`) — один контекст без профиля на диске (кэш только в памяти,
умирает с перезапуском vite). Адрес экрана — `<профиль>--<цель>--<ячейка>.localhost:4320` (`store/app/live-url.ts:56`, `cellOf`):
у каждой ноды свой origin, поэтому у каждой свой раздел HTTP-кэша и кэша скомпилированного кода.
Ячейки придуманы для iframe (общий sessionStorage вкладки); в трансляции каждая страница — отдельная вкладка со своим sessionStorage.

Замер measurements/cache-exp.mjs: 8 страниц админки korbor сразу, Helium headless, 1440×900.

| Вариант | Запросов | Скачано | CPU браузера, с | Все готовы, с |
|---|---|---|---|---|
| dev, ячейки (как сейчас) | 4880–6552 | 270–419 МБ | 42–48 | 12,9–13,7 |
| dev, общий origin роли | 4880–6065 | 28–34 МБ | 37–42 | 10,8–12,1 |
| dev, общий origin + профиль на диске, 2-й запуск | 4889 | 0 | 26,8 | 8,0 |
| прод-сборка админки (vite build 1,4 с), холодно | 159 | 2,7 МБ | 22,4 | 6,7 (первая 1,5) |
| прод + профиль на диске, тепло | 88 | 0 | 13,2 | 7,2 |

Выводы: тормозит выполнение ~600 dev-модулей на страницу, а не сеть. Порядок выигрыша: прод-сборки приложений (CPU ×3,
запросов ×50) > профиль на диске в живущем отдельно браузере (CPU −35 %) > общий origin (трафик ×8).
Свой движок или пересборка Chromium — отвергнуто: рендер React-приложений = Blink+V8, своего не написать; сборка Chromium — 100+ ГБ и часы на каждое обновление.
