# Состояния экранов и компонентов для Live App Map

Результат работы — один файл `.live-app-map/states.ts` в корне проекта. Код приложения не меняешь.
Live App Map установлен в `$LAM_HOME` (по умолчанию `~/.live-app-map`); ниже `<lam>` — этот каталог, `<проект>` — абсолютный путь корня проекта.

## Контракт

Типы — в пакете `@live-app-map/sdk` (`node_modules/@live-app-map/sdk/dist/project.d.ts`). Прочитай их перед работой, не пиши по памяти.

```ts
import type { LamComponentFixtures, LamScreenStates } from '@live-app-map/sdk';

export const screens: LamScreenStates = {
  'miniapp:route:/feed': [
    { id: 'empty', label: 'Пустая лента', kind: 'empty',
      api: { 'GET /api/v1/recruiter/feed': { status: 200, body: { items: [], total: 0 } } },
      note: 'Нет вакансий: заглушка «Пока пусто» и кнопка «Обновить»' },
    { id: 'filters-open', label: 'Фильтры открыты', kind: 'ui',
      steps: [{ click: 'role=button[name="Фильтры"]' }, { waitFor: 'role=dialog' }] },
  ],
};

export const components: LamComponentFixtures = {
  'apps/miniapp/src/shared/ui/Button.tsx#Button': [
    { id: 'primary', label: 'Основная', props: { variant: 'primary', children: 'Откликнуться' } },
  ],
};
```

- Ключ `screens` — id экрана из карты (`nodes[].id`), дословно.
- Ключ `api` — `МЕТОД /путь` с `:параметрами` ровно как `code.apiCalls[].path` в карте. Значение — `{ status, body?, delayMs? }` или `'pending'` (ответ не придёт — загрузка).
- `kind`: `data` | `empty` | `error` | `loading` | `ui`. `role` — id роли из `config.apps[].roles`; нет — первая роль приложения.
- `steps` выполняются после загрузки страницы по порядку: `click`, `fill` + `value`, `press`, `waitFor`, `scroll` (пиксели). Селекторы — Playwright: `role=button[name="Создать"]`, `text=Фильтры`, css.
- Ключ `components` — `<файл от корня проекта>#<имя экспорта>`.

## Шаг 1. Карта

1. Свежая карта: `cd <lam> && bun run scan -- --project <проект>` (`--` обязателен) → `<проект>/.live-app-map/map.json`. Сканируй заново, если код экранов менялся после даты файла.
2. Пустой `baseUrl` в `.live-app-map/config.ts` — остановись и попроси пользователя вписать адрес dev-сервера; без него экраны не откроются.
3. Из `map.json` выпиши экраны: `nodes[]` с `kind: "page"` — `id`, `pathPattern`, `source.file`. Список экранов не придумывай и не сокращай: каждый экран из карты либо получает состояния, либо попадает в отчёт с причиной.

## Шаг 2. Данные экрана

Для каждого экрана:

1. Вызовы API экрана: `code.screens[]` с `nodeId === id` экрана → `calls[].callId` → `code.apiCalls[]` (`method`, `path`, `routeId`, `location` — где вызов в коде, `via` — через какой компонент).
2. Роут бэкенда: `code.routes[]` с `id === routeId`: `response.fields` (поля ответа), `response.values` (что возвращается: переменная или вызов), `response.statuses` (явные статусы), `input` (схемы body/query/params), `access` (вход, роли).
3. Если ответ — строка из БД (`values: ["findVacancy()"]`), типы и допустимые значения полей бери из `code.tables[].columns` (`type`, `enumValues`, `notNull`). Есть MCP Live App Map — то же через `get_route`, `get_table`.
4. Прочитай код экрана (`source.file`) и компонентов из `via`: какие поля ответа он реально читает, что рисует при загрузке, пустом списке и ошибке, где форматирует даты, деньги, статусы.
5. Вызова нет в `code.apiCalls`, а экран грузит данные (обёртка не распознана) — путь и метод бери из кода вызова, в отчёте отметь «вызов не найден сканером: <файл:строка>».

## Шаг 3. Состояния экрана

Для экрана с GET-вызовами — минимум четыре состояния:

| kind | id | api |
|---|---|---|
| data | `data` (или `data-<что>`) | 200, тело с 2–5 правдоподобными записями, которые заполняют все ветки разметки (разные статусы, длинный и короткий текст, есть и нет картинки) |
| empty | `empty` | 200, пустой список / `null` в той форме, которую возвращает роут |
| error | `error` | статус из `response.statuses` (нет — 500), тело в формате ошибок этого бэкенда (найди общий обработчик ошибок) |
| loading | `loading` | `'pending'` для главного вызова экрана |

Несколько GET-вызовов — в каждом состоянии подменяй все, иначе второй уйдёт в живой бэкенд и смешает данные. Ошибка второстепенного вызова, которую экран рисует отдельно (виджет, счётчик) — отдельное состояние `error-<что>`.

UI-состояния (`kind: 'ui'`) — всё, что видно только после действия: модалки, шторки, выпадающие меню, вкладки, шаги многошаговой формы, раскрытые фильтры, ошибки полей после отправки, подтверждение удаления. Ищи в коде экрана `useState`/стор, которые переключают `Dialog`, `Sheet`, `Drawer`, `Popover`, `Tabs`, `step`, и условия показа ошибок. Каждое — `steps` до нужного вида и `waitFor` по элементу, который появился. Ошибка поля после отправки — `fill` + `click` на отправку и `api` мутации с ответом ошибки (статус и тело по `input` и коду обработчика: например 422).

Экраны с ролями (`access.roles` роута, разные ветки кода по роли) — состояния под каждую роль, `role` в состоянии, id с суффиксом роли: `data-employer`.

## Шаг 4. Компоненты

1. Найди общие компоненты: `src/shared/ui`, `src/components/ui`, `packages/ui` — экспортируемые React-компоненты.
2. Для каждого — варианты по пропсам из его типа: `variant`, `size`, `disabled`, `loading`, `error`, пустое и длинное содержимое. `props` — только сериализуемые в JSON значения; `children` — строка.
3. Компонент сам ходит в API — добавь `api` варианту, как у экрана.
4. Не тащи в галерею страницы и одноразовые компоненты экрана.

## Правила качества

- Ни одного выдуманного поля: каждое поле в `body` есть в `response.fields`, в колонках таблицы или читается кодом экрана. Сомнение — открой обработчик роута (`code.routes[].handler.location`).
- Значения правдоподобны для предметной области проекта, на языке интерфейса; даты — фиксированные ISO-строки, без `Date.now()`/`Math.random()`; id записей — в формате, который ждёт код (uuid, число).
- `id` состояний и вариантов — строчные латинские, цифры, дефис; уникальны в пределах экрана/компонента. `label` — коротко по-русски. `note` — что видно на экране и зачем состояние.
- Только `import type` из `@live-app-map/sdk` — в рантайм приложения ничего не попадает.
- Файл проходит проверку типов: `bunx tsc --noEmit --strict --module esnext --moduleResolution bundler --skipLibCheck .live-app-map/states.ts` — 0 ошибок.

## Шаг 5. Проверка в визуализаторе

1. Dev-серверы приложений проекта запущены, в их `vite.config` подключён `lamVite()` из `@live-app-map/sdk/vite` (без него подмена API не работает — скажи пользователю).
2. Визуализатор: `cd <lam> && bun run dev -- --project <проект>` (http://localhost:4310).
3. MCP Live App Map для агента (один раз): `claude mcp add live-app-map -- bun run --silent --cwd <lam> mcp`.
4. Каждое состояние:
   - открой его в визуализаторе (узел состояния рядом с экраном) или прямо в браузере: `<baseUrl><путь экрана>?lam_state=<encodeURIComponent(id экрана + "/" + id состояния)>`;
   - `get_visualizer_state` — что открыто; `request_snapshot` с заметкой «состояние <id>» → пользователь выделит экран → `get_snapshot` даёт PNG — посмотри его;
   - есть браузер (Playwright, MCP браузера) — открой адрес сам и сделай снимок.
5. Брак, который исправляешь сразу: экран такой же, как в `data` (подмена не сработала — ключ `api` не совпал с путём вызова); белый экран или окно ошибки рантайма (поле не той формы); шаг не нашёл элемент (селектор по тексту, которого нет); в `loading` нет индикатора загрузки.
6. Не смог проверить (нет dev-сервера, нет снимка) — так и пиши в отчёте, не «готово».
